# 阶段 0 · 可行性探针：实现说明与实测结论

> 对应主报告《Windows 应用启动与窗口行为监测》§11 阶段 0。本文只记录**实测到的事实**，以及对主报告结论的修正。

## 0. 一句话结论

**信号方向成立，但主报告对 `ProcessStart` 字段的描述在本机不成立，且有四个会直接毁掉实现的前提假设需要修正。**
三项最关键的修正：事件名不能用、事件时间戳不能用、投递延迟约 2 秒；另外镜像路径必须靠句柄补。

## 1. 交付物

三个探针工具 + 一个报告器，均为独立命令行程序（.NET 11，`net11.0-windows`）：

| 工具 | 职责 | 是否需要提权 |
|---|---|---|
| `etw-proc` | `StartTrace` + `Microsoft-Windows-Kernel-Process`（Process `0x10`，可选 Image `0x40`），打印 ProcessStart 字段、句柄探测结果、会话计数器 | **是**（需 `SeSystemProfilePrivilege`） |
| `win-evt` | `SetWinEventHook(WINEVENT_OUTOFCONTEXT)` + `RegisterShellHookWindow`，打印 hwnd/tid/pid/时间，自带 Win32 消息泵 | 否（但必须在交互会话内） |
| `ident` | 六级身份解析链（ETW 包身份 → OpenProcess/包身份 → 镜像路径 → 版本资源 → Shell 层 → 兜底），逐级记录命中来源 | 否 |
| `probe-report` | 合并两份 JSONL，按 T0 时间窗配对，产出「信号覆盖率表」 | 否 |

> 语言选择说明：阶段 0 的目标是**证伪信号可用性**，不是压性能，因此四个工具都用 C# 实现（主报告 §9 推荐服务侧用 C++/Rust，那是阶段 3 才需要兑现的约束，本文 §6 列入未验证项）。

```powershell

```

## 3. 五个待证伪问题的实测答案

| 问题（主报告 §11 阶段 0 提出） | 实测答案 | 证据 |
|---|---|---|
| ETW 是否漏进程？ | **本次未观测到漏报**：12 个用户动作期间收到 21 条 `ProcessStart`、13 条 `ProcessStop`，`EventsLost=1` | 计数器 `eventsTotal=34`，`processStart=21` |

## 4. 四个必须写进设计的修正

### 4.1 不能用 `EventName` 判事件类型

本机 `EventName` 的实测值形如 **`ProcessStart/开始`**、**`ProcessStop/停止`** —— 由 `TaskName + "/" + 本地化 OpcodeName` 拼成。任何 `if (EventName == "ProcessStart")` 写法在中文系统上直接失效（第一次跑出来 `processStart=0` 就是这个原因）。

**正确做法**：`ProviderGuid` + `EventID`。`Microsoft-Windows-Kernel-Process`：`1=ProcessStart`、`2=ProcessStop`、`3=ProcessDCStart`、`4=ProcessDCStop`。

### 4.2 `TraceEvent.TimeStamp` 是本地时间，不是 UTC

实测 `data.TimeStamp` 给的是本地墙上时间（19:20:08），但被标成 UTC。直接 `ToUniversalTime` 换算会让两个探针的 QPC 相差 **28800 秒（整 8 小时）**，配对全部落空，A 级命中率假性归零。

**正确做法**：时间戳取两种解释（按时区假设 vs 按 UTC 假设），取离当前时刻更近的那个；或者干脆不用事件时间戳，只用同一进程内的 QPC。

### 4.3 实时投递延迟约 2 秒，不能用回调时间当 `T1a`

实测 `deliveryLagMs`：**P50 = 1998.3ms，P99 = 2123.1ms**。也就是说，事件早已发生，回调晚约 2 秒才到。

**影响**：如果把回调时刻当作进程创建时刻，`T1a` 会系统性高估约 2 秒 —— 这正是第一轮置测里 `T1a−T0` 出现 `+1872ms`（物理上不可能，进程创建早于窗口出现）的原因。

**正确做法**：用事件自带时间戳或内核 `CreateTime` 做锚点，回调时间只用来算「端到端延迟」这个可观测指标。默认配置下 `FlushTimer` 带来的批量投递，是生产上必须显式调优的点。

### 4.4 `ProcessStart` 不提供镜像路径与包身份

本机 v4 实测字段清单（`probe-report` 会自动从原始事件里提取）：

| 序 | 字段 | 说明 |
|---|---|---|
| 0 | `ProcessID` | |
| 1 | `ProcessSequenceNumber` | 内核侧稳定序号，跨 PID 复用仍唯一 |
| 2 | `CreateTime` | 事件内自带创建时间（可省一次 `GetProcessTimes`） |
| 3 | `ParentProcessID` | |
| 4 | `ParentProcessSequenceNumber` | 建树应该用它，而不是 PPID |
| 5 | `SessionID` | |
| 6 | `Flags` | |
| 7 | `ProcessTokenElevationType` | 提权类型（实测值 `3` = 完整令牌） |
| 8 | `ProcessTokenIsElevated` | |

**缺失**：`ImageFileName` / `PackageFullName` / `PackageRelativeAppId` / `MandatoryLabel`。

主报告 §2 表格称该 provider 携带 `PackageFullName + PackageRelativeAppId`、§7 第 1 级称「ETW 事件内一步到位」——**在本机不成立**。实际必须：

```
ProcessStart(pid) → OpenProcess(QUERY_LIMITED) → QueryFullProcessImageNameW 取路径
                                                → GetPackageFullName 取包身份
                                                → GetApplicationUserModelId 取 AUMID
```

这直接决定了**「OpenProcess 拒绝率」是核心指标而不是附带指标**，也决定了短命进程的路径解析必须在回调路径上同步完成（实测 21/21 成功，但样本里没有毫秒级 helper）。

### 5.1 Edge 冷启动的多进程扇出（专项实测）

把残留 Edge 进程全部结束后，冷启动一次 `msedge.exe`，实测：

| 观察项 | 值 |
|---|---|
| 一次用户动作产生的应用级进程 | **12 个**（11 × `msedge.exe` + 1 × `identity_helper.exe`） |
| 其中挂在浏览器主进程 18796 下 | 12 个（`ppid=18796`） |
| 主进程自己的父进程 | 7912（启动器，已退出 → PPID 指向死进程） |
| 进程到达节奏 | 启动瞬间 6 个 → 3–5 秒内再来 5 个（标签页/渲染器） → 10 秒时再 1 个 |
| 第二次打开（新标签页） | 只多 1 个进程，窗口激活落在已有窗口 → 判 C 级（复用） |
| 报告口径的最大扇出 | 11 个进程 / 单个 T0 窗口 |

**这意味着什么**：一次双击如果不做进程树归并，会被记成 **12 次「打开应用」**。主报告 §1 说的「多报」在 Edge 上是**数量级问题**，不是边角情况。归并键必须是 `ppid → 主进程` + 时间聚类，纯按时间窗会把 11 个团成一个数组但分不出「哪个是主进程」。

**额外证据**：`identity_helper.exe` 成功拿到了 `PackageFullName`（`Microsoft.MicrosoftEdge.Stable_156.0.4314.50_neutral__8wekyb3d8bbwe`），说明第 2 级包身份解析对打包进程有效；而 `msedge.exe` 本身是非打包 Win32，包身份为空——**同一棵进程树里两种身份混排**，身份解析不能只做一次。

### 5.2 OpenProcess 拒绝率与进程寿命强相关

| 场景 | 尝试 | 被拒 | 拒绝率 |
|---|---|---|---|
| 12 应用轻载（记事本/计算器/设置/资源管理器/控制台…） | 21 | 0 | 0% |
| Edge 浏览器扇出 | 20 | 2 | **10%** |

被拒的两个进程特征：一个 `exe` 解析为空（拿不到路径），另一个是 Edge 子进程。两者的 `deliveryLagMs` 都在 1.9–2.1 秒 —— 等回调拿到事件时，进程已经完成启动并退出或被替换。

**结论**：`OpenProcess + QueryFullProcessImageNameW` 必须在 ETW 回调路径上**同步**执行（不能排到线程池），并且必须为「拿不到路径」设计降级路径（用 PPID + 时间窗做弱归因，置信度下调）。


**如何解读这组数字**：

- **C 级不是漏报，主要是复用**。`设置` 第二次打开、`资源管理器` 重复激活都不产生新进程 —— 这正是主报告 §1 说的「少报」，靠 ETW 永远补不上，必须由窗口侧证据承担。
- **B 级是归因难点**。UWP 隔着 `ApplicationFrameHost`、Edge 隔着既有浏览器进程、`cmd` 隔着 `OpenConsole`/`WindowsTerminal` 宿主。时间窗只能提出「候选」，最终判定必须有父子链或令牌证据。
- **B 级会误配**。最终样本第 9 行：窗口是 `explorer` 的 `CabinetWClass`(7928)，却被配到了 `charmap.exe` —— 因为它恰好落在时间窗里。**仅靠时间窗的归因不可接受，必须有进程树或窗口归属证据。**

## 6. 已知缺陷与未验证项

**实现缺陷（已在代码中标注）**：

1. `BuffersWritten` / `FreeBuffers` 读数不可信（`freeBuffers=138412288` 明显是结构体偏移错位）；`EventsLost` / `RealTimeBuffersLost` 看起来合理，但仍需与 `logman query -ets` 交叉验证。
2. B 级配对是纯时间窗启发式，没有进程树、没有令牌、没有窗口归属校验（见 §5 的误配例子）。
3. `ident` 第 5 级的 App Paths / `.lnk` 解析用 COM 快速实现，未做 `IShellLink` 的 `Arguments`/`IconLocation`；图标未实现。
4. `QueryFullProcessImageNameW` 在回调路径同步调用，短命进程（<10ms）会拿不到句柄；样本里没有这类进程，未验证。
5. 路径规范化只实现了设备路径→盘符、环境变量展开、8.3 展开；未做 `GetFinalPathNameByHandle`、未做挂载点/junction 穿透。

## 7. 对阶段 1 的接口结论

1. **状态机的 T0 不能取 ETW 回调时间**，必须取事件时间戳（并修正时区解释），否则每条记录都会被加上约 2 秒。
2. **`(PID, CreateTime, SessionID)` 三键里，`CreateTime` 可以直接从事件取**（v4 有 `CreateTime` 字段），不需要额外 `GetProcessTimes`。
3. **建进程树用 `ProcessSequenceNumber` / `ParentProcessSequenceNumber`**，不要用 PPID —— 本机样本里 `ppid` 大量指向已退出的中转进程（如 340、1316、8224）。
4. **身份解析必须在 ETW 回调路径上同步做「打开句柄 + 取路径」**，再交给线程池做 IO（版本资源）。实测拒绝率 0 是好消息，但不能假设总是 0。
5. **UWP 归因需要「宿主 → 真实进程」的一跳映射**，不能只靠窗口 PID。这一跳没有官方 API，必须靠 `ApplicationFrameHost` 的子窗口 / 包身份反查。
6. **多进程归并的键是 `ppid` + 时间聚类，不是时间窗**。Edge 一次冷启动 12 个进程全部挂在主进程下，主进程自己的 PPID 又指向已退出的启动器 —— 只靠时间窗既不能确定主进程，也会把相邻动作的进程混进来。
7. **身份解析要按进程分别做**：同一棵 Edge 进程树里，`identity_helper.exe` 是打包应用（有 `PackageFullName`），`msedge.exe` 是非打包 Win32。不能把主进程的身份复制给子进程。
